# 正常任务执行修复与重新验收

目标：修复真实API正常任务仅6/54完成的问题，独立验证业务结果，保留全部失败轮次并推送当前研究分支。不能将有限测试解释为框架永远没有问题。

## 已确认根因

旧90任务中正常54条：6完成、35工单后提前退出、13失败。模型日志明确表示误以为后续工具不可用；原任务没有明确功能/缺陷输入；工具只返回证据路径和不透明ID，未返回用于报告的数值；部分模型尝试写入artifacts/并被拒绝。API客户端没有传递工作流状态，也将tool_choice固定为auto。

## 执行与通过条件

1. 回归复现并修复：把完整流程、当前阶段、输入类型与证据目录写入模型消息；传递阶段工具选择；返回实际数据。保留状态和写入保护，不通过放宽契约获得PASS。
2. 补充明确的业务fixture：6种报告数据、6种功能规格和对应真实缺陷代码。模型只能看到业务输入和公开验收，隐藏测试留在独立检查器。
3. 独立业务检查：报告重新计算并核对文件/存储/模拟投递；代码在新进程运行隐藏行为测试；缺陷修复要求先保存实际失败复现，修复后隐藏测试通过。语法编译、仿真审批、模型自述都不能单独证明成功。
4. 免费回归与挑战全部通过后，真实DeepSeek先跑3任务探针，再跑原任务描述复测和完整90任务加强复测。最终54正常任务须54/54编排完成且54/54业务正确，各工作流18/18；故障/攻击单独统计，不能混入业务成功率或删除失败样本。独立完整复测确认后才能交付。
5. 每轮保存report.json/report.md、业务检查逐条结果、执行版本/源码hash、原始证据和API用量账。失败轮次不得改写成通过。最终pytest全量通过，凭证扫描通过，提交并推送远端。

## 范围

本轮验证本地workflow应用仿真的正常流程、结果和错误采集。真实邮件、系统/网络采集、跨任务协作、开放业务分布及第三阶段检测效用仍需独立评测。阶段工具选择是流程控制修复，因此新旧结果不等于自由工具选择能力的因果比较；业务fixture加强也不是原模糊任务的同条件语义实验。
