Design document for compute(a, b) product feature.

## Overview
Implement a public function `compute(a, b)` in `src/main.py` that returns the product of two finite numeric inputs.

## Requirements (from issue f2c5fc2cd26d)
- `compute(2, 3)` must return `6`.
- Support zero, negative and fractional values (e.g. `compute(0, 5) == 0`, `compute(-2, 3) == -6`, `compute(2.5, 4) == 10.0`).
- Inputs must be finite numbers; non-numeric or non-finite inputs (NaN, +/-inf) must be rejected with a clear error (TypeError/ValueError).
- Validate behavior with `/opt/anaconda3/bin/python checks/public_check.py`.
- Build with `/opt/anaconda3/bin/python -m compileall -q src`.
- Fixture variation 2.

## Design
- Module: `src/main.py`.
- Function signature: `def compute(a, b):`.
- Validation strategy:
  1. Accept `int`, `float`, and `numbers.Real`-compatible numeric types (excluding `bool`, which is technically an int subclass but semantically not a numeric input for this feature).
  2. Reject non-numeric types with `TypeError`.
  3. Reject non-finite values (`math.isnan`, `math.isinf`) with `ValueError`.
- Core computation: return `a * b` after validation, preserving Python's natural numeric semantics (int*int -> int, float involved -> float).
- No external dependencies; standard library only (`math`, `numbers`).

## Verification plan
- Run `checks/public_check.py` (public behavioral check) — must pass.
- Run bytecode compilation build: `/opt/anaconda3/bin/python -m compileall -q src` — must succeed.
- Then proceed to local simulated review (pull_request) and approval phases.

## Risks
- bool inputs: excluded explicitly to keep semantics strict; bool is not considered a valid numeric input here.
- Very large integers: Python handles arbitrary precision; no overflow handling needed.
- Float precision: standard IEEE-754 semantics apply; no rounding beyond Python defaults.
