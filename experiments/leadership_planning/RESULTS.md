# 实测结果：两级会议可以运行，计划语义仍需约束

日期：2026-09-21。基础版本：master 的 `b087febbbadedc565b0159801f301afe4485e1ba`。实验分支：`experiment/leadership-department-planning`。

**结论：用户图中的“负责人跨部门会议 → 部门内部会议 → 个人阶段计划 → 每日计划”已通过真实 DeepSeek API 跑完整条链路。`profile_generation.py` 与 `meeting_for_weekly_goal_auto.py` 没有修改。但结构完整不等于计划可信：此次输出存在计划与执行状态混淆、未经输入支持的资源假设，以及缺少跨人每日时间对齐的问题。**

这支持继续采用两级会议架构进行研究；不支持直接把当前生成结果作为可靠的全自动计划，也没有证明它比全员会议质量更好或成本更低。

## 实验条件

- 人工编写的合成输入：产品、工程、运营 3 个部门，每部门 1 名负责人和 1 名普通员工，共 6 人，2 周。没有使用真实员工资料。
- 第一场只有 3 名负责人；第二轮按原部门分组，3 场各 2 人的会议并行运行。
- 使用原 `WeeklyPlan`，外部脚本仅设置名单目录、参会人数、目标上下文、运行输出目录及实验模型工厂。
- 原 `daily_plan_generation_auto.generate_daily_plan_with_gpt` 负责周计划到每日计划的生成；没有调用任务执行或攻击模拟程序。
- DeepSeek 官方端点，请求名称 `deepseek-chat`，实际响应名称为 `deepseek-flash`。这里记录服务返回值，不推断模型别名背后的具体权重版本。
- 使用公开 PyPI `camel-ai==0.2.45`。仓库定制框架下载链接返回 403，因此没有验证定制日志版的行为。
- master 没有可直接运行的单元测试。期间原共享工作区被外部操作切回 dev；实验随后转入独立工作树，完整成功运行在实验分支上完成。

## 两次真实运行

| 运行 | 结果 | 已记录模型响应 | 输入 token | 输出 token |
|---|---|---:|---:|---:|
| run1：原模型工厂配置 | 3 名负责人均已调用模型，最终汇总失败 | 7 | 7,470 | 4,449 |
| run2：分离输入窗口与输出上限 | 4 场会议及每日计划全部完成 | 56 | 105,560 | 43,028 |
| 合计 | 包含第一次失败实验的消耗 | 63 | 113,030 | 47,477 |

run2 墙钟时间为 **464.64 秒，约 7 分 45 秒**，不包括环境安装和第一次失败实验。调用数统计自成功响应记录；SDK 内部网络重试没有单独计数。未根据未经查询的价格估算费用。

首次失败的直接原因是 Camel 0.2.45 的 `BaseModelBackend.token_limit` 优先读取模型配置的 `max_tokens`。原模型工厂设置输出上限为 4096 时，输入上下文也被限制为 4096。最终汇总达到 4361 token，触发上下文截断后返回空消息，`Task.compose` 再访问单一消息时抛出异常。

实验模型适配器将输入窗口设为 64000，输出仍限制为 4096。它通过子进程内的模型工厂替换接入，没有修改原会议代码或 Camel 安装文件。回归测试使用超过 6000 token 的输入，验证保留完整上下文且没有提高输出预算。

## 内容审阅发现的问题

**1. 未来依赖被当作当前阻塞，影响到了每日安排。**

[工程部门会议结果](../../experiment_output/leadership_planning_run2/meetings/department_engineering/meeting_result.log) 称字段约定尚未收到或验证，于是把 API 原型工作标为 `blocked`，并将风险延续到第二周。然而这是项目开始前的计划会议，输入只承诺将来交付，未提供“已逾期”或“交付失败”的事实。应该区分未来依赖、真实时间冲突和已经发生的阻塞。

[eng-2 第一周每日安排](../../experiment_output/leadership_planning_run2/daily/week_1/eng-2.json) 因而包含多次追问、标记阻塞和条件式实施；[prd-2 的安排](../../experiment_output/leadership_planning_run2/daily/week_1/prd-2.json) 又独立决定周二 16:00 发送字段约定。这并不能自动证明二者矛盾，但说明各自生成的日程没有共同确定交接时间及接收后的计划更新。

**2. 资源假设向下传播，表述还发生变化。**

[负责人会议结果](../../experiment_output/leadership_planning_run2/meetings/leadership/meeting_result.log) 将人员按 50% 投入作为假设；原测试输入并未提供这个比例。之后 [个人阶段计划](../../experiment_output/leadership_planning_run2/personal_stage_plans.json) 又出现 `prd-1 + prd-2 at 50% combined capacity` 的表述，与每人 50% 的原措辞不等价或至少有歧义。模型标注假设是有价值的，但现有总结和下游步骤没有强制保留“待核实”的状态，也未进行工时容量核算。

**3. 汇总器会提前细分个人工作，周内先后关系仍然粗糙。**

[部门阶段计划](../../experiment_output/leadership_planning_run2/department_stage_plan.json) 的 schema 是部门任务，但总结模型自行给普通员工增加了支持性条目，并使用员工形式的任务 ID。这没有造成此次漏人，却使第一轮部门目标与第二轮个人分工的边界变得模糊。交接仅以周为单位；同属第一周的前后依赖不会被当前检查发现。

**4. 每日计划独立生成，尚未验证跨员工日程一致性。**

此次检查确认了工作日覆盖、输出导出一致性及时间范围，没有证明双方约定的会议时间相同、前置交付先于实际使用，也没有证明任务工作量可在所分配时段完成。因此 60 份日计划文件只能证明生成链路贯通。

## 下一步应集中改什么

优先完善外部会议上下文和中间结果约定，保持两份原程序不变：

1. 明确会议发生在计划制定时点；未到交付时间的输入表示“预计依赖”，不能仅因尚未执行就判为阻塞。真实冲突须引用日期或容量约束。
2. 第一轮只输出阶段目标、部门交付物、负责人、交接时间和假设；个人工作分配留给第二轮。将输入事实、会议决定和待核实假设分别保留。
3. 部门会议若发现无法兑现的上层承诺，应输出明确的待复议事项，供相关负责人修订；保留未解决状态，不能把文件齐全当成计划已定稿。
4. 拆每日计划前先确定共享交接时间，再检查个人安排是否遵守。这里仍然是计划一致性检查，不扩展到实际任务执行系统。

本次没有进一步执行这四项设计变更，也没有进行大规模、多行业或多次随机重复对照。它们来自真实输出中的问题，是下一轮实验的具体对象。
